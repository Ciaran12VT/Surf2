# Persistence, remote resources and live SQL implementation specification

Status: the local Surf2 resource milestone in section 13 is implemented in the working tree. Section 16 records setup, verification and remaining environment qualification. The Azure persistence/transfer sections remain a later implementation plan.

Original baseline: `relationalDb_V2`, commit `b0830ddfa201758ec26c810f02cd43c60cb61014` (`history load`). Compatibility and conversion requirements below were checked against `Azure_Step1_Local`, commit `c69db27df554b35a275ce3da28b980bcf06b2ed7`, including the subsequent preference and durable-link changes. The local resource implementation advances that baseline to schema 3 and package 3.

Replace the single connection editor in Settings > Persistence with a local connection catalogue, separate Local and Azure grids, a read-only current-connection label, and connection-to-connection transfer. A user must be able to work against an existing Azure SQL Database using the same relational persistence services as local SQL Server.

Scope resources must also support remote Git repositories, Azure Blob folders and live SQL databases alongside local folders and independent database snapshots. All source types work with either local or Azure SQL persistence. A migration plan can relocate external files and rebind references when the destination environment cannot access the original locations.

The supplied mock-up, handwritten relationships and latest annotated diagram define the requested behavior. The implementation keeps Surf2 persistence local; Azure SQL is supported as an external live source. No user's database has been migrated during implementation.

## 1. Scope and decisions

The first milestone keeps the Surf2 application's own database local. It delivers Git resources, Blob resources and paired-folder reconciliation, then live SQL and linked snapshots. A live source can be local SQL Server or Azure SQL Database regardless of where Surf2 stores its own data. The Persistence connection switch, migration to shared Azure persistence, profiles, permissions, and private versus shared resources are later work. The existing transfer design remains in sections 3–9 and 12 for that milestone.

The full design also includes a connection catalogue, a single startup default, read-only connection testing, workspace switching, selected-connection export/import and database transfer. The local milestone uses the resource designs in sections 10 and 11. The later transfer path supports local-to-Azure, Azure-to-local and same-platform transfers.

The following choices define the behavior. Replacement of an existing target after confirmation and a recovery export is confirmed by the user; the other details complete the implementation design.

| Topic | Behavior |
| --- | --- |
| Current versus default | Current identifies the database actually used by this running workspace. Default selects the next ordinary startup. Changing either does not implicitly change the other. |
| Azure grid fields | Use the same columns as Local. Server, database and authentication belong in the connection-string dialog, avoiding two conflicting copies of connection settings. |
| Meaning of Local | SQL Server connections outside the Azure SQL Database category, including LocalDB, SQL Express and network SQL Server. It does not mean the legacy local JSON persistence store. |
| Transfer | Copy all supported Surf2 application data from source to destination; leave source data unchanged. No merging or continuous synchronization. |
| Existing target data | **Replace the target's Surf2 contents after explicit confirmation and a verified recovery export.** Empty and supported Ready V2 targets are eligible. Source remains unchanged. Replacement is required for this release; merging is outside scope. See section 9 for publication and recovery rules. |
| Azure provisioning | Connect to a database provisioned outside Surf2. Surf2 may initialize its schema after explicit user confirmation, but does not provision Azure servers, databases, networking or accounts. |
| Legacy formats | Recognize legacy Surf2 storage and explain migration requirements. Only a supported Ready relational V2 database can become current directly. Preserve the existing separate legacy migration workflow. |
| Blob and local folders | Add Blob resources in Scope Setup. Connect to an existing container or create one in a selected storage account. An ordinary folder and a Blob location can be used independently or explicitly paired under one node. For a pair, detected local changes unload it immediately; check remote Blob changes only at startup, explicit Refresh or Load. |
| Git repositories | Use one Object Explorer node per repository in a scope. A user can attach their working folder, a direct Git connection, or both. The direct connection uses a persistent Surf2-managed checkout and both views use the same folder reader. |
| Local cache | Keep managed Git checkouts and Blob copies across launches. Check active Blob sources for changed files on startup. Settings exposes per-source and total storage limits, usage and cleanup. Decline downloads that would exceed those limits or available space. |
| Live SQL source | Add an explicit live database resource for local SQL Server or Azure SQL. Browse metadata/definitions and query any accessible table without capturing it first. Its ordinary business database is not subject to the Surf2 persistence-format gate. |
| Snapshots | Preserve generated-SQL import, direct capture and exported-folder import. A snapshot remains self-contained and requires no live connection to its original database. |
| SQL source credentials | Pasted SQL-results and exported-snapshot imports require no source SQL credentials in Surf2. Direct snapshot capture and live SQL querying require verified visibility/definition access to every supported object in the declared source scope and SELECT access to its table data. The same credentials may serve both direct features. |
| Resource relocation | Before SQL publication, optionally switch local Git references to verified remote Git, copy selected files to Blob, or rebind to an existing Blob location. Support the inverse materialization to local folders. Apply mappings only to destination state. |
| Proposed query scope | First release provides generated table queries and editable, parameterized, single SELECT queries in a dedicated read-only query view. It does not provide SQL administration or write-through grid editing. Section 11 defines the limits. |

Surf2 supports creating a Blob container in an existing storage account. SQL servers/databases, storage accounts and networking are provisioned separately. Standalone Blob resources use local cache refresh. Paired folders use reviewed reconciliation in both directions. Explicit content transfer for persistence relocation is part of the later migration milestone.

### Interpreting the diagram

Three relationships must remain distinct: **reference/read** an external source; **capture** independent content into a snapshot; and **copy/replace** Surf2 persistence. A black arrow into a Surf2 database means its workspace can register and use that source; it does not mean ingest every external file or table into Surf2 SQL storage. The red arrows represent persistence transfer; the blue arrows represent explicit materialization or rebinding, not continuous synchronization.

This table retains the original handwritten numbering. The annotated diagram extends relationships 1 and 2 to both directions and clarifies live SQL versus snapshot behavior.

| No. | Relationship | Implementation meaning |
| --- | --- | --- |
| 1 | Remote Git ↔ local Git folder | Identify correspondence; use a remote reference or materialize a selected remote revision locally. Local changes need an explicit preservation choice before rebinding. |
| 2 | Blob folder ↔ local folder | Pair locations under one node and switch the active view. A reviewed relocation plan can also copy files between locations. |
| 3 | Local Git folder → local Surf2 DB | Register a local folder source; show Git branch and repository details. |
| 4 | Local folder → local Surf2 DB | Retain existing folder parsing, rendering, search and references. |
| 5 | Local SQL source → local Surf2 DB | Register a live SQL resource with metadata browsing and explicit table queries. |
| 6 | Local SQL source → snapshot held locally | Capture/import independent definitions and selected data; future viewing needs no source connection. |
| 7 | Local Surf2 DB ↔ Azure Surf2 DB | Copy all supported Surf2 state into Empty or compatible Surf2 targets; populated targets require confirmation and a verified recovery export. |
| 8 | Remote Git → local Surf2 DB | Use the remote URL to prepare a managed checkout and browse, read and index it through the folder reader. |
| 9 | Blob folder → local Surf2 DB | Cache and index the selected container or prefix on the desktop. |
| 10 | Azure SQL source → local Surf2 DB | Use an Azure SQL business database as a live resource. |
| 11 | Azure SQL source → Azure Surf2 DB | Same live-resource behavior with independently located persistence. |
| 12 | Azure SQL source → snapshot held in Azure | Capture/import a portable snapshot into the active Azure Surf2 store. |
| 13 | Remote Git → Azure Surf2 DB | Same Git provider and logical resource bindings with Azure persistence. |
| 14 | Blob folder → Azure Surf2 DB | Same Blob provider and logical resource bindings with Azure persistence. |
| 15 | Azure SQL source → snapshot held locally | Capture/import remotely sourced data into local Surf2 persistence. |

Apply the same independence to combinations not drawn explicitly: a local SQL source can feed a live resource or snapshot in Azure-backed Surf2 when reachable from the running desktop. A snapshot's storage location never determines its source location.

### Logical model

| Concept | Stored where | Responsibility |
| --- | --- | --- |
| Persistence connection | Protected local catalogue | Select the Surf2 application database; current/default and format eligibility apply here. |
| Source definition | Surf2 relational state, without credentials | Stable source ID, provider and versioned locator/configuration for LocalFileSystem, AzureBlob, Git or LiveSql. Local Git is a detected capability of LocalFileSystem. |
| Resource Container | Surf2 relational state, owned by one Scope | Stable public identity, scope-specific name/order and default Resource. Own one or more alternative Resources; display one explorer node using the active Resource's icon and children. |
| Resource | Surf2 relational state, owned by one Resource Container | Concrete source or snapshot/diagram binding, with its own stable identity, alias, locator and IncludeChildren. Exactly one Resource per container is effectively active on a desktop. |
| Local selection and cache | Per-user desktop settings and app-owned storage | Record the selected Resource by scope/container/resource public IDs and manage local copies. Use the container default when no valid local choice exists. Shared containers default to the remote Resource. |
| Authentication binding | Protected local user storage | Map a source ID to this user's connection/authentication material; never export secrets in the Surf2 package. |
| Source item/document binding | Surf2 relational state | Stable resource and item identity, independent of temporary cache paths. Normal opening and session restoration resolve the resource's current navigable content. |
| Database snapshot | Surf2 relational snapshot/history tables | Independent materialized definitions and captured rows. Optional provenance is descriptive, never a required source connection. |
| Relocation plan | Local operation journal plus destination mapping records | Approved source-to-destination mappings and verified content manifest, separate from SQL replacement status. |

The hierarchy is **Scope → Resource Container → Resource → Resource Child Objects**. Object Explorer projects the container and its active Resource as one node. Its first child switches to another Resource, offering a chooser when several exist, or links an appropriate alternate source when only one exists. Files, folders and database objects follow that action row. Adding another verified checkout or direct connection for the same Git repository adds a Resource to the existing container rather than another independent repository node. Each alternative retains its own root/subfolder and branch selection.

Independent snapshot resources remain allowed even when their database origin matches. Adding/importing a matching snapshot offers adding a version to a selected existing snapshot resource or creating a separate snapshot resource/container. **Restore To** always creates the separate resource/container without this duplicate-detection question. An upgrade preserves existing separate snapshot histories and never merges them automatically.

Source configuration edits create a new configuration revision. Saved documents retain their intended resource/item identity until explicitly rebound; renaming an alias does not change source identity. Configuration revisions prevent stale operations or endpoint edits from reinterpreting a binding against an unrelated source; they do not pin an individual document to historical content. A source and a persistence connection may point at the same technology, but they have different roles, permissions and lifecycle.

Normal Object Explorer navigation exposes only the latest saved version of a database snapshot resource. Git navigation exposes the working files of the selected checkout, at its current branch/commit, including local edits for a user-managed checkout. Restored ordinary documents resolve those current contents rather than a remembered historical revision. Keep the existing document refresh/reload behavior; this milestone does not introduce per-document version selection or persistent content pinning.

Database snapshot history remains available through the existing History and Comparison functions. Their selected historical versions and windows are session-only and are not restored on application restart. Preserve the stored history itself. **Restore To** creates a separate snapshot resource whose restored content becomes its own current navigable state. Commit IDs, Blob ETags/version IDs and snapshot revision keys remain useful internally for consistent reads, cache validation, history/comparison and transfer verification; they do not imply a requirement to persist historical versions in ordinary document links.

Unloading a Resource automatically closes its open files/objects and dependent resource views. This applies to manual and automatic unload for every resource type. Unloading the displayed Resource Container closes views owned by its member Resources; it does not delete the container, source data or snapshot history. Section 10 defines the lifecycle and reconciliation rules.

At the baseline commit, the database format is `Surf2.RelationalV2`, **schema version 2**. The format probe recognizes schemas 1 and 2 with version-specific checksums; normal runtime requires the current schema. Schema 2 stores captured rows as JSON in `surf.FullTableData`; generated `capture.Data_*` tables belong to schema-1 compatibility. The package identifier is `Surf2.RelationalV2.Package`, package version 2. The exporter emits schema 2; the importer accepts schema 1/2 and converts schema-1 captures before Ready publication. Product V2, database schema and package versions are separate values.

The local milestone targets relational **schema 3** and **package 3**, retaining the identifiers `Surf2.RelationalV2` and `Surf2.RelationalV2.Package`. Set the schema's minimum reader and writer versions to 3. Keep exporter-contract version 1 and row-encoding version 1 if their existing manifest/stream encoding remains unchanged; validate the entire supported version tuple rather than accepting any combination of those numbers. Export the current schema/package by default and support explicit conversion of older inputs. Do not offer an implicit downgrade. Add shared-persistence maintenance/replacement metadata in its later milestone with a further version change when required. Once a schema or package contract is released, freeze it; later feature slices requiring additional persisted structure must receive a new version rather than redefining a released version 3.

### Supported inputs and conversion routes

| Input | Required route to the local milestone |
| --- | --- |
| Empty application database | Install schema 3 directly and validate before activation. |
| Ready relational schema 3 | Validate the current contract and activate without repeating backfill or generating new identities. |
| Ready relational schema 2 | Normalize supported preference additions, then perform the explicit 2→3 resource-model upgrade. Preserve the application's database identity. |
| Ready relational schema 1 | Run the existing resumable 1→2 generated-capture-to-JSON conversion, validate schema 2, then run 2→3. |
| Recognized interrupted 1→2 conversion | Resume that converter first; its marker may still say schema 1 with reader/writer minimum 2 and partially populated FullTableData. Do not mistake it for a Ready schema-2 database. |
| Relational package 2 containing schema 1 | Validate/decode with the frozen package-2/schema-1 contract, convert generated captures, then apply the resource-model conversion before schema-3 publication. |
| Relational package 2 containing schema 2 | Validate/decode with the frozen package-2/schema-2 contract, including supported preference projections, then convert the resource model before publication. |
| Relational package 3 containing schema 3 | Validate and import the current contract without an older-model conversion. |
| Legacy SQL document store, supported local JSON state, or legacy ZIP FormatVersion=1 | Retain the existing staged, separate-destination legacy conversion, then convert its relational output to schema 3 before normal activation. Preserve the original source. Legacy format 1 is not a relational package version 1. |
| Older generated SQL results or snapshot display-export folders | Continue through their existing snapshot importers. Before publishing an explicit snapshot import, show the section 11 origin warning/review dialog when origin is unknown or incomplete; let the user supply details or continue with the missing information explicitly recorded. These import one snapshot's available content, not an entire Surf2 workspace or full-fidelity database backup. |
| Unknown/future format, unknown checksum, corruption or unsupported table/column shape | Reject with the specific compatibility problem. Unsupported versions/shapes and corruption detectable in preflight fail before destination writes. Corruption found later while streaming an empty-target import leaves that destination non-Ready; a populated-target replacement rolls back. Never activate a partial import, invent defaults for unknown authoritative data, or silently discard it. |

An interrupted legacy migration resumes only against its matching staged manifest, migration identity and fingerprint. An incomplete relational package import remains unavailable: the current importer requires a fresh Empty destination and does not support resumption. Do not route every database marked Migrating into a general upgrade routine. Distinguish upgrade, legacy conversion and package-import ownership before recovery.

### Versioned installation, upgrade and package publication

1. **Freeze historical contracts.** Keep published `001.*` and `002.*` scripts unchanged. Replace `ReadScripts`'s current “schema 1 or all scripts” logic with explicit manifests for schemas 1, 2 and 3. Make the historical capture converter request `ReadScripts(2)` explicitly when recording its schema-2 checksum. Define immutable authoritative table/shape catalogues for each package/schema combination; do not derive old catalogues by filtering the newest mutable table list.
2. **Dispatch before creating a normal runtime.** Probe exact format/version/checksum and operation state. Route Ready old databases to the upgrade coordinator, recognized interrupted operations to their own recovery path, and packages to the matching decoder. Preserve the existing source database identity on in-place upgrade. A fresh imported database receives its own identity and rowversions while retaining portable scope/resource/snapshot public identities.
3. **Protect and isolate an in-place upgrade.** Stop normal/background work, drain connections and establish exclusive upgrade access; a new application lock alone cannot exclude older clients that do not acquire it. Recheck identity/version, then create and validate a recovery export under the source version's contract while retaining exclusion through upgrade publication or reconciled failure. The existing exporter requires the current schema, so add a bounded compatibility export path for supported Ready schema 1/2 rather than relabelling older data as schema 3. Test/Probe remains read-only. An already interrupted 1→2 operation follows its existing validated resume protocol and retains any original recovery artifact before 2→3 begins.
4. **Complete 1→2 where needed.** Retain the dataset-by-dataset conversion and validation of generated capture tables into FullTableData. Do not replace it with a schema-version marker update. Do not run it against an indiscriminately installed schema-3 target: it currently accepts schema 1/2 only. Complete and validate the schema-2 representation before the next conversion.
5. **Apply 2→3 and publish atomically.** Normalize supported preferences, add the resource/binding structures and backfill identities within one transaction where practical. Validate ownership, default membership, preservation mappings, current snapshot pointers, history and assets. Record schema 3, reader/writer minimum 3 and the exact schema-3 checksum in that same successful publication. Rollback leaves schema 2 usable if 2→3 fails; a completed preceding 1→2 is not automatically reversed. If backfill later requires batching, specify a resumable upgrade journal and non-Ready admission gate before adopting that implementation.
6. **Decode old packages before transforming them.** Validate original archive entries, metadata, counts and hashes using their own frozen contract. Use a schema-2-compatible unpublished conversion destination for package-2/legacy adapters, or an equally validated staged representation; never expose an intermediate Ready workspace. Convert captures and the resource model, then validate against an explicit transformation map/expected-output fingerprint. Preserve exact verification for original fields and separately validate documented new/default/mapped fields. Do not globally relax metadata or byte/hash comparison. Update importer ownership/publication checks, which currently hard-code schema 2.
7. **Publish only complete current state.** New empty-target imports may retain bounded batch loading while unpublished, but all conversion and validation must finish before Ready. The later populated-target replacement retains its separately specified transaction. Extend package export selection, TextContent/Asset reference closure, FK ordering/cycle handling and reset/validation plans for new authoritative tables. Keep legacy migration evidence and derived/cache/credential data excluded. Reopen a fresh runtime, perform existing durable-link repair, and rebuild indexes only after successful publication. A lost acknowledgement is resolved by probing the committed version/identity; never replay backfill blindly.

Current export emits package 3/schema 3. Retain import adapters for package 2/schema 1 and 2, with exporter-contract/row-encoding version 1 and their existing consistency/local-file policies. Update `InspectPackageAsync` to return enough version information to select the adapter, not merely Legacy versus Relational. Unsupported future exporter/row-encoding versions still fail explicitly. Keep input packages unchanged. After converting an old package, re-export/re-import as package 3 must preserve the converted authoritative state.

Legacy conversion continues to support only its known scope, snapshot, diagram, workbench, workspace and settings roots plus referenced image assets. It is not a general restoration of arbitrary archived AppData, caches or connection settings. Snapshot display-folder imports also retain their existing fidelity warnings: displayed SQL/CSV cannot recover omitted history, original typed values or absent origin metadata. Extend generated SQL's Database payload and future display-export sidecars with optional versioned origin fields, while accepting older payloads/sidecars. Explicit snapshot imports offer the section 11 origin review after decoding; automatic schema conversion preserves unknown origin without prompting or inventing evidence. Origin matching and the append-versus-separate snapshot choice run after decoding, not as a schema migration that merges existing data.

## 4. Connection catalogue and migration

Keep the catalogue on the user's computer, independently of whichever SQL database is current. Saving a name, connection or default must not require a working database or publish unrelated pending Settings preferences.

| Field | Purpose |
| --- | --- |
| `Version` | Catalogue serialization version, initially 2. |
| `Revision` | Optimistic concurrency token for local catalogue writes. |

Retain the invariant even if two instances move the default simultaneously.

Migration is local and idempotent:

1. Recognize the old single `ConnectionString` file. Preserve its effective connection behavior, assign a stable ID, derive an editable name from the database or `Existing connection`, and make it the default.
2. Classify known Azure endpoint names as Azure; otherwise preserve as Local and allow the category to be corrected in the connection dialog. 3. Protect the string and atomically publish the new file. Preserve compatibility defaults that were effective for an existing local connection; flag an old Azure connection requiring secure-option correction rather than silently treating it as trusted.
4. With a genuinely missing file or a valid legacy blank connection, create the built-in LocalDB default record. This creates configuration only, not a SQL database.
5. An unreadable, malformed, future-version or undecryptable file opens a connection-recovery UI. Do not overwrite it or silently select another database. Allow explicit repair or creation of a replacement catalogue.

Do not keep a plaintext migration backup. Exclude this file, its pending/backup variants and any credential material from persistence packages and diagnostic logs. A catalogue copied to another Windows identity may require credentials to be re-entered; do not treat decryption failure as an empty catalogue.

## 5. Database testing and eligibility

**Test connection string** parses and opens the selected connection, then runs read-only format and required metadata checks. It must not create a database, install a schema, change database options or write a probe row. A successful SQL login alone is insufficient.

| State | Display beside ConnectionString | Meaning and permitted actions |
| --- | --- | --- |
| Untested | Neutral dash and `Not tested` | Test/edit/remove/default allowed; activation/transfer/export/import require a fresh successful classification. |
| Testing | Busy indicator and `Testing` | Cancellable; prevent duplicate tests for that row. |
| Empty | Green tick and `Empty database` | May initialize and become current after confirmation; valid import/transfer target. No source data to export/transfer. |
| Ready | Green tick and `Surf2 V2` | Supported schema and Ready marker. May become current, export, be a transfer source, or be replaced as a destination after confirmation and a recovery export. |

Keep accessible text and tooltips with every icon; color alone is insufficient. Distinguish `Cannot connect`, `Cannot verify database contents`, `Migration required`, and `Import incomplete` in the detailed explanation.

Reuse `PersistenceFormatProbe` checks for the exact format identifier, supported schema and reader/writer versions, marker structure, singleton, nonempty database identity, state and schema checksum. Keep its conservative emptiness rule: no user objects/types/schemas and sufficient metadata visibility. Failure to see tables due to permissions must never qualify a database as empty. Block system databases such as `master`, `model`, `msdb` and `tempdb` from initialization/activation/transfer.

Testing must remain read-only even when it recognizes a schema that can be upgraded. Show `Surf2 — upgrade required` with an explicit preparation action before activation/transfer. Today startup automatically upgrades schema 1 to 2, and today's exporter cannot export schema 1 directly. The new workflow must disclose and separately confirm any required source/target schema preparation, including an interrupted-upgrade recovery, before transfer preflight. Transfer itself leaves source data unchanged; do not conceal a source-schema mutation inside that promise. Preserve the existing resumable capture conversion and its identity/data guarantees.

Recognizing a compatible format does not prove that every write/export permission exists. Check capabilities for the requested operation separately; retain the green format result but show a specific permission error when an operation is unavailable. Do not mutate data to test permissions.

Capture a row ID, connection revision and immutable options snapshot when testing. Discard a result if the row was edited, removed or superseded before completion. Changing connection text, category or credentials resets status to Untested; changing only Name/default does not. Refresh affected status after initialization/import/transfer and when an operation detects that the database changed.

Re-probe endpoints immediately before operations, even if a green badge exists. Pin database identity and format through the operation. A badge is a last observed status, not authorization to skip checks.

## 6. Setting the current connection

**Set as Current** takes effect in this running application through a controlled workspace handover. Merely saving a connection for restart does not satisfy this command.

1. Commit pending row edits and capture the selected connection. Freshly probe it and verify operation permissions. If already current with the same effective connection, return without reloading.
2. For a verified empty database, ask `Initialize this empty database for Surf2 and open it?`, naming the endpoint. 3. Resolve unsaved documents, diagrams, workbenches and settings through the existing save/discard/cancel flow. Saves belong to the old runtime. Cancellation or save failure stops the switch.

After commit, cleanup problems must not change which database the label identifies.

Startup precedence remains: explicit external-open/environment override, saved default, built-in fallback only when bootstrap configuration is genuinely absent as described in section 4. ## 9. Transfer contract and target policy

Display `FROM: [connection]  TO: [connection]  [OK]` as in the mock-up. Use the union of both saved grids, with group/name and safe endpoint details. Show ineligible entries disabled with their reason; orange rows cannot be selected at all. Drafts never appear. Untested rows require Test before becoming selectable.

FROM requires a supported Ready V2 database. Empty databases show `No Surf2 data to transfer` and cannot be a source. TO accepts either Empty or supported Ready V2, including a database with existing data. A Ready target displays `Existing Surf2 contents will be replaced after a recovery export`. Clear a selection if an edit/test makes it ineligible. Enable OK only with two eligible, distinct endpoints and no operation already running. Check replacement capability during preflight; failure to establish safe exclusive access stops the operation with a reason.

Reject source and destination that resolve to the same physical database, even through different names, credentials or aliases. Use the existing `SameDatabase` logic as a starting point, verify its server/database identity behavior on Azure, and combine it with canonical endpoint evidence and pinned Surf2 identity. Neither connection-string equality nor a copied Surf2 marker alone proves distinct physical databases. If distinction cannot be established, stop before writes with an explanation.

### Transfer sequence and confirmation

1. Capture both connections and block conflicting edits/operations. Freshly test format, permissions, supported schema and physical separation. Complete any separately confirmed compatibility preparation. Resolve pending unsaved work if this application's current database is either endpoint. Target saves complete before taking its recovery snapshot.
2. Export a consistent source snapshot to an operation-owned local temporary package using `RelationalPackageExporter`. For package import, pin the selected archive instead. For replacement, perform a full bounded streaming validation pass over the input, including every table/local-file stream, declared counts and hashes, before target mutation. Keep the package immutable through validation and use.
3. Build the resource relocation plan in section 12 from the pinned package, including **Keep existing references** when appropriate. Show one final confirmation naming FROM (or package), TO, content-copy destinations, inaccessible references and any intentional differences. For a Ready target, state `Replace all Surf2 data in <target> with <source>? Its existing contents will first be exported to <recovery path>. The source and your default connection will remain unchanged.` Use **Replace target contents** and **Cancel** buttons. Display a unique recovery filename in a persistent user-selected folder; do not overwrite an older recovery file. For Empty, confirm import/initialization without claiming existing data needs a recovery export. After confirmation, stage/verify approved external content before taking target maintenance access; report any copies left behind if subsequent SQL publication fails.
4. Recheck the pinned target identity and format after confirmation. If it changed, stop and request a new preflight/confirmation. For Ready, establish the maintenance exclusion below, export and fully verify the recovery package, then run transactional replacement. For Empty, retain the existing fresh-target importer and migration lease; do not initialize it as Ready first.
5. Apply the approved locator/source mappings while importing destination state. Validate all imported data, mapped bindings and constraints, publish Ready last, and verify the committed operation and new identity. Reopen a current target with fresh runtime state; otherwise leave current untouched. Report destination, relocation results, any unresolved references, available counts and the retained recovery-package path, and refresh its badge.
6. Dispose connections/leases and remove only disposable temporary source files owned by the operation. Keep the recovery export after success, cancellation or failure. Report cleanup problems and retain operation evidence required for reconciliation.

Maintain the exporter's consistent snapshot requirement. Where snapshot isolation is unavailable, offer the existing explicit SERIALIZABLE blocking alternative with an explanation that source writers may wait; never silently weaken consistency or enable database options. No distributed transaction spans the two servers. Source consistency ends at the exported snapshot; later source changes are not included.

### Maintenance access and schema compatibility

Add a database-scoped maintenance admission protocol and durable operation journal. A proposed `surf.PersistenceOperation` record holds operation ID, kind, status, expected old/new database identities and source/recovery package hashes. A durable local journal records the same operation ID, connection-record ID/revision, safe physical target identifiers, source package reference and recovery path/hash; store no credentials or decrypted connection strings in either journal. Exclude operational records from exported application data.

All normal persistence operations must acquire shared admission before checking readiness/identity and retain it through their SQL work. Write paths acquire it in the same transaction that performs the write, and recheck identity/format after acquisition. Cover state, snapshots, capture, background index work, schema changes and import; a check before a later transaction is insufficient. A replacement coordinator holds exclusive admission continuously from before the target recovery snapshot until publication or reconciled rollback. Retain the existing migration lease too, with one documented acquisition order to avoid deadlocks. Maintenance-owned exporter/validator work must use the coordinator's authorized context rather than deadlock waiting for normal admission.

Use database-scoped application locks with explicit ownership, bounded waits and checked return codes. Session locks disappear when the owning session ends, so durable recovery gating remains necessary after disconnection. [SQL application locks](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql?view=sql-server-ver17)

The baseline migration lease coordinates import/migration only; it does not exclude ordinary writers. Introduce a versioned schema upgrade and reader/writer compatibility gate for this new protocol. Drain and exclude pre-protocol client sessions as part of enabling it, and reject older clients on reconnect. An application lock does not constrain old clients or independent SQL writers that ignore it. Require exclusive maintenance access against those writers too; if it cannot be established, refuse replacement before replacing application data. Never treat a successful migration lock alone as proof of exclusivity.

Update exact schema/checksum validation, installer scripts, supported reader/writer versions and package compatibility together. Preserve a read/export/upgrade path for the baseline schema, and an explicit import mapping for its existing version-2 packages; do not label every baseline database unusable after introducing the feature. Compatibility preparation is separate from the destructive replacement: explain and obtain confirmation for a required schema upgrade, preserve application contents through that upgrade, and finish it before the final replacement confirmation and recovery snapshot. Cancelling replacement does not undo a separately completed upgrade.

### Recovery export

Under exclusive maintenance access, export the target's complete supported Surf2 state using the package contract, then verify the finished archive by streaming every entry and checking structure, counts and hashes. Flush and atomically publish the file before replacement may begin. Record its operation ID, manifest hash, size and path in the durable local journal and retain an immutable read lease. Recheck ownership/target identity before proceeding. A failed export, verification failure, disk-space/permission problem or cancellation stops replacement with the old application data intact.

The recovery export represents the target immediately before replacement; no other writer may change it between that snapshot and publication. It contains the target's application state and SQL assets, with the same external-file and credential exclusions as ordinary export. It is a persistent recovery artifact, not a temporary file, and is never silently removed on success. Completion and recovery views provide **Open recovery folder** and instructions to import it into an empty database, or explicitly replace a compatible target through this same guarded workflow.

### Transactional replacement

Implement a distinct replacement service. Reuse package codecs, whitelists and validation logic; refactor the loader/validators to accept one caller-owned SQL connection and transaction. **Do not invoke the existing batch-committing `ImportAsync` against a cleared target.** Every target-side mutation and validation, including bulk-copy batches, `surf.FullTableData` JSON streams, legacy capture conversion where applicable, identity reseeding, constraints, mapped bindings, derived-state rebuilding and publication, must use that same transaction. Existing validators that open separate sessions must be adapted to see the uncommitted replacement. The current FullTableData importer commits each payload independently; it requires adaptation along with ordinary row loaders. Do not use per-batch or per-dataset internal transactions.

`SqlBulkCopy` supports an existing `SqlTransaction`, allowing multiple copy operations and other changes to commit or roll back together. Use that contract for the replacement batches. [Transactions and bulk copy](https://learn.microsoft.com/en-us/dotnet/framework/data/adonet/sql/transaction-and-bulk-copy-operations)

Within one target transaction at SERIALIZABLE isolation, clear/replace the known Surf2 application content, load the source package, apply reviewed reference transformations, rebuild derived state, validate models/content/constraints, and assign a fresh database identity and rowversion values. Include the completed operation ID, input/mapping hashes and expected-output fingerprint in final publication. Commit only after all checks pass. Preserve the target database/server, users, roles, grants, network settings and local connection record. Retain installed schema/object permissions; for any owned object recreated by the restore, record and reapply its explicit permissions within the same transaction, or refuse during preflight if they cannot be preserved. Only known application-owned content may be reset. Inventory objects, triggers and dependencies before replacement; unexpected objects or dependencies that prevent a complete safe replacement cause preflight failure, not arbitrary object deletion.

The source's scopes, resources, history, captures, diagrams, workbenches, preferences and assets replace the corresponding target state in full. No old target application records remain merged into the result. Keep target maintenance/compatibility metadata under the new service's ownership rather than importing source operational records.

Use bounded buffers even though there is one transaction. Estimate required client disk space and target transaction-log/data capacity, enforce tested replacement size/time budgets, expose progress/cancellation, and report service-tier capacity or timeout limits clearly. If the transaction cannot complete within supported limits, roll it back and retain the old target; do not silently switch to destructive batch commits. Cancellation may require a long rollback: show `Rolling back` and keep normal use blocked until the outcome is confirmed. A future staged publication implementation must meet the same failure contract before it can replace this path.

When the target is current, suspend its workspace, resolve unsaved work and close/drain target-bound windows and operations before maintenance. On commit, invalidate every old locator/cache/session and load the replacement using a fresh owner as in section 6. Keep the connection's name/ID/default choice. On rollback, reopen the old target after reconciliation. Reopening failure after a confirmed commit is reported as `Replacement completed; workspace could not reopen`, with retry/recovery access; it is not reported as an uncommitted transfer.

### Failure and recovery outcomes

| Point of failure or cancellation | Required outcome |
| --- | --- |
| Before replacement confirmation, or during source preparation | Target application contents unchanged; no replacement. A separately confirmed compatibility upgrade may remain. |
| During recovery export/verification | Old target application data unchanged; report recovery failure and do not start replacement. |
| During transactional replacement before commit | Roll back the whole target transaction. After rollback is confirmed, the old application state remains available; keep the verified recovery file. |
| Connection loss or crash around commit/rollback | Mark outcome unresolved and keep normal use blocked until the server-side operation record, old/new identity and package fingerprint establish the result. Never automatically replay replacement. |
| Commit confirmed | Report success even if cancellation/connection loss arrived afterward; retain recovery export and reload any current target. |
| Empty-target import fails after batches committed | Preserve the existing non-Ready `Migrating` behavior. Show orange `Import incomplete` and require a fresh target or a separately verified recovery operation. This does not describe replacement of a populated target. |

Persist intent before mutation and commit completion evidence with the new contents. A maintenance record left unresolved after a crash must prevent ordinary activation/writes until a recovery coordinator establishes committed success or completed rollback; recovery is available independently of a working main workspace. Re-probe and reconcile before retrying. Do not treat a recovery ZIP as proof that a failed replacement was rolled back, and do not automatically restore it over a target whose commit outcome remains unknown.

The ordinary History/Comparison version selector lists content versions, without duplicate V10 entries for unchanged refreshes. Refresh attempts and their outcomes are available in snapshot details.

Show the active snapshot's version, name and both timestamps in its details/header, using this format:

`V10 NexusDev - Captured at [last actual revision update] - Last Refreshed [last time a refresh was run]`

**Captured at** is the capture timestamp belonging to the current content version; it remains unchanged when a refresh finds no changes. **Last Refreshed** shows the most recent completed refresh attempt's time and outcome. A successful unchanged attempt is marked No changes in its details. Failed or cancelled attempts must be explicitly labelled, for example `Last Refreshed [time] (failed; last successful refresh [time])`, so the latest attempt cannot imply that the stored content was successfully verified. While running, show Refreshing with the start time without replacing the previous completed outcome. Keep the most recent successful refresh separately. Store timestamps in UTC and display them in the user's local timezone with an unambiguous date/time format. Use Not yet refreshed/Unknown when no recorded event exists rather than inventing a timestamp.

Create a refresh record with a stable operation ID before source work begins and record completion as Changed, Unchanged, Failed or Cancelled. Interrupted or unknown publication outcomes remain explicitly unresolved until recovery determines whether publication committed; never manufacture a successful refresh after a crash. Successful completion and the resulting version binding must commit in the same transaction as snapshot publication, including its unchanged-content path. Retries/recovery of that same operation must not add duplicate events or advance the content version again. Failures/cancellation record their outcome without changing the last successful timestamp or content. Keep diagnostics free of credentials and table-row contents.

Associate each event with its acquisition method and observed source/origin evidence. An initial capture can record a successful event; a manual SQL-results or exported-folder import applied as an update records that import, not a claim of a fresh live source read. Show its method and any known source capture time separately from the time the import was applied. Simply opening a snapshot, restoring a full application package or using Restore To does not count as refreshing from the source. Package restoration preserves recorded events; a separate restored snapshot retains available historical capture provenance without inventing a new source refresh.

Change the capture comparison path as well as the displayed timestamps. `RuntimeDataEqualAsync` currently compares data-set ImportedAtUtc and `SnapshotValueEquality.Table` compares FullDataImportedAtUtc, so a new timestamp alone can prevent reuse of identical full-table data. Introduce content-comparison semantics for refresh that ignore acquisition/refresh timestamps and observation provenance while retaining actual schema, definitions, selected data, capture selections and other content differences. Keep exact persisted-value comparison for package validation and historical reconstruction; do not globally weaken those checks. Do not rewrite immutable data-set/table timestamps to make equality pass. If another object changes, retain the original capture time of reused resource revisions while the new snapshot version records its own capture time.

The current unchanged-publication path can update `DatabaseSnapshot.ImportedAtUtc`; do not use that mutable catalogue value alone as the displayed content capture time. Read the current version's immutable capture time (or a separately preserved known capture time for legacy content without a VersionKey). Extend summary/UI contracts with revision capture time, last attempt and outcome, and last successful refresh. Unknown legacy timestamps stay unknown; a schema upgrade must not create a fictitious refresh or content revision. Include event records in package export/import and verify their version/source reference closure. The later enrichment of origin evidence must not rewrite the original revision's capture time or provenance.

### Requested table data when tables change

A full-table-data selection targets the source's **schema and table name**, with any saved TOP/WHERE selection. On each capture, resolve that name against the current catalog. A previously observed SQL object ID is not a permanent binding or a reason to reject a replacement table. Apply these rules:

| Current source state | Capture behavior |
| --- | --- |
| Requested table exists | Capture its current data using its current metadata/column layout and the saved selection. |
| Requested table is confirmed absent | Skip that table's data capture and list **Skipped — table no longer exists** in the completion summary. Allow the otherwise successful snapshot to publish with the table absent. Do not create an empty-table placeholder or carry its previous rows into the new snapshot. |
| A different table now has the same schema and name | Automatically capture the replacement's current data and schema. Do not require an object-ID rebinding prompt or assume that its columns match the earlier table. |
| Table has a new name or schema | The old selection remains absent; do not infer a rename or transfer its row filter to a different name. A table under the new name requires its own full-data selection. |
| Existence/access is unverified, or a read fails | Report the actual failure and do not publish a successful direct capture. Missing visibility, SELECT denial, timeout, invalid filter and interrupted enumeration are not confirmed absence. |

Retain the requested schema/name and selection in the saved capture configuration even when the table is skipped, unless the user explicitly removes the request. Keep requested selections separate from the list of data sets actually captured; this allows a later table under the same name to be captured automatically. Prior snapshot versions retain their original metadata and full table data, including for tables now missing or replaced. New capture publication updates current membership without deleting historical revisions or rewriting their captured data layouts.

For direct capture, use section 11's complete-access qualification to establish absence. Refactor `RelationalDatabaseCaptureRequest`/`RelationalSourceTable` so a saved request need not carry a still-valid positive object ID, and resolve each request to a current source table before reading. In `RelationalDatabaseCaptureService`, replace the prior-selection object-ID mismatch rejection and the blanket missing-selection failure with explicit captured/confirmed-absent/failed outcomes. Preserve every requested selection in the published configuration; the current implementation only adds selections it successfully encounters. Validate metadata, row counts and rows against the same resolved table for that capture attempt. If it changes again during capture, discard the inconsistent unpublished attempt and re-resolve safely, or fail without publication; never combine one table's schema with another table's rows.

Retain supported TOP/WHERE selections when resolving a same-name replacement. A predicate that remains valid applies to the current table. If changed columns make it invalid, report the error and retain the previous successful snapshot; never silently remove the predicate or substitute an unrestricted read. Preserve quoting, query validation and capture limits.

The generated manual SQL path already guards requested table-data blocks with `IF OBJECT_ID(..., N'U') IS NOT NULL`. Keep name-based capture and skip-when-absent behavior aligned across generated SQL and direct capture, and verify the generated script against missing and recreated tables. Manual SQL execution uses the user's external SQL session; importing its output or a Surf2 export still requires no source credentials in Surf2. An import must not invent absent-table data or remove data from earlier versions. A metadata visibility failure must not be presented as verified absence merely because `OBJECT_ID` returned NULL.

### SQL credentials and effective access qualification

| Operation | Source credentials and access requirements |
| --- | --- |
| Import pasted results of the generated snapshot SQL | No source credentials are entered or used by Surf2. The user runs the SQL externally using their own SQL tool/session, then imports its output. Apply import validation and origin review without requiring a live connection. |
| Import a Surf2-exported snapshot folder | No source credentials or live connection are required. Read the supplied files and apply the existing import validation/origin review. |
| Direct snapshot capture or **Refresh Snapshot** | Authenticate to the source and qualify both complete visibility/schema-definition reading and table-data SELECT access across its declared scope before capture. Publish only a fully validated capture. |
| Live SQL metadata browsing and table queries | Use the same access qualification. Every in-scope table must support its intended table-data reads; query execution remains explicit and bounded. The same source authentication binding can serve live queries and direct capture. |

The declared scope is the selected source database and its supported user tables, functions, triggers, stored procedures and views, restricted only by explicit supported source filters. It must never be inferred as merely the objects the login happens to see. Without an explicit filter, qualify all supported user objects in that database. Selecting only certain tables for full-data snapshot capture does not narrow the required metadata coverage or the table-data access qualification.

Require effective permissions to discover every object in that scope, read its schema and applicable definitions, and SELECT its table data, including required columns. Database-scoped `VIEW DEFINITION` and `SELECT` are typical grants for a whole-database source, but inherited grants, more specific denials and column exceptions affect effective access. Do not require `db_owner`, `sysadmin`, write permissions or EXECUTE permission on business procedures merely to inspect their definitions. An account that already has broader privileges can be used if it passes the read checks; Surf2 still exposes only its supported read operations. Do not grant/revoke permissions, install helpers, execute business routines or change database options as part of Test. [Metadata and definition visibility](https://learn.microsoft.com/en-us/sql/relational-databases/security/metadata-visibility-configuration) · [Effective permission checks](https://learn.microsoft.com/en-us/sql/t-sql/functions/has-perms-by-name-transact-sql)

Implement a source-session qualification result with separate outcomes for **Qualified**, **Insufficient access**, **Unable to verify complete access**, and **Required definition unavailable/unsupported**. Bind it to the source identity/configuration, actual authenticated context and declared scope. Establish a demonstrably complete object inventory before evaluating individual objects: checking only returned `sys.objects`/`sys.tables` rows cannot detect hidden objects, and a single database-level permission check is not sufficient proof. Use a validated audit of applicable effective permissions/session principals, or an independently trusted, current complete inventory available through an explicitly configured read-only metadata mechanism. Such a mechanism must not change the principal used for the actual definition/data reads or be installed automatically. If the available evidence cannot prove coverage, report Unable to verify rather than claiming the account definitely lacks a permission or recommending ownership by default.

Against that complete inventory, check effective object/column permissions and read the required metadata/definitions using the actual source session. Use permission functions such as `HAS_PERMS_BY_NAME` plus bounded, safely quoted zero-row table reads over the required columns where appropriate; those reads test access without downloading table contents, but do not themselves prove inventory completeness or guarantee every later query will succeed. Account for role/group permissions, explicit schema/object/column restrictions and the visibility limits of permission catalogs. `sys.database_permissions` alone is not a complete effective-permission evaluator. Validate the non-owner proof path on supported SQL Server and Azure SQL versions before enabling the feature. [Permission catalog and column exceptions](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-database-permissions-transact-sql)

Requalify on Connect/Load, explicit source refresh, changed credentials/source/scope, and direct capture; before an explicit query, validate its authenticated context and relevant object/column access. Do not treat an earlier Test result as permanent authorization. Actual read/capture failures remain authoritative. On required-access failure, stop direct use, cancel pending work and unload the live Resource through the shared close lifecycle. Keep its connection record visible with the failed capability/object and a useful remedy. An independent saved snapshot stays usable without those source credentials. Manual import options remain available. Distinguish inaccessible metadata from encrypted or otherwise unsupported definitions; additional permissions do not necessarily make encrypted source text readable.

Record successful direct capture only after both access qualification and the capture succeed, allowing explicitly reported skips for requested tables confirmed absent. Publish a content revision only if the captured state changed; an unchanged successful refresh records its event against the existing version. If a selected table exists but its rows cannot be read, report the failed capture and keep the prior revision. When a verified complete catalog shows that a formerly captured table is absent, show its removal in the new revision. Compare tables by schema and name, so a rename appears as the old name removed and the new name added; a same-name replacement is captured automatically under the requested-table rules above. Preserve historical rows under their original revisions. Source row-level filtering or masking remains effective during reads; SELECT permission is not a promise to bypass those controls or expose data beyond the authenticated session's access.

Keep snapshots and live sources visibly distinguished in the resource picker and explorer. A snapshot resource exposes its latest saved capture; older versions are accessible through History and Comparison. Refresh on a live source queries its current state without changing a saved snapshot unless a snapshot capture is explicitly requested. Source deletion or credential loss must not break an existing snapshot. All local/Azure source and persistence combinations use the same capture/import contract when the source is reachable from the desktop.

Deliberately different content requires explicit acceptance and produces changed/unresolved document states rather than claiming the reviewed source bytes were preserved.

### Cross-service failure and recovery

There is no transaction spanning SQL, Blob, Git and the filesystem. Track resource phases separately: Planned, Staging, Verified, SQL publication pending, Published, Cleanup pending/Failed. | Failure point | Required outcome |
| --- | --- |
| Before external staging | No content copied or target application state changed. |
| During upload/download | Target references unchanged; retain a resumable operation-owned manifest or offer cleanup of only verified operation-owned artifacts. |
| After staging, before SQL commit | Original locations and target state remain intact; report staged copies. Do not describe SQL rollback as having undone external writes. |
| SQL outcome unknown | Retain all evidence and staged content; block replay/cleanup until operation identity/receipt establishes the result. |
| SQL committed, credentials unavailable on another client | Keep the published resources visible as requiring authentication; do not undo committed transfer or substitute other sources. |
| Cleanup requested | Delete only operation-owned artifacts proven unreferenced by published state and retained recovery plans. Never remove original source content, shared prefixes, user checkouts or files needed for rollback recovery. |

Completion reports copied/rebound/kept/unavailable resources, file counts and verification results, the SQL result and recovery path, and any retained staging artifacts. Exporting the old target for recovery preserves its old external references; the transfer must not alter/delete the external content they require.

## 16. Local milestone implementation and operation

The local resource implementation adds `ResourceContainer`, provider-backed resource members, `ResourceWorkspace` and `LiveSourceWorkspace`. Explorer projects one active member per container and keeps alternate members in the stored scope. Its first child links or switches sources and supports mouse and Enter activation. Current document locators use resource/item identity rather than managed cache filenames. Local selection stays on the desktop; ordinary saved windows resolve current content.

**Getting started**

1. Open Scopes and use **Git Repo**, **Add Blob** or **Live SQL**. Local folders remain available through **Folder**. Use the node's first child to attach or select an alternate source.
2. Git requires Git for Windows on `PATH`. HTTPS authentication uses Git Credential Manager; SSH uses the user's configured SSH credentials/agent. Surf2 does not modify the user's working checkout. A managed checkout is reused until explicit refresh.
3. Blob accepts an existing HTTPS service endpoint/container/prefix, or explicitly creates a private container in an existing account. Authentication options are Entra sign-in, SAS and anonymous access. SAS and SQL connection credentials are protected in desktop-local storage and excluded from exports.
4. **Settings → Local Cache** shows retained Git/Blob copies and total local source storage. Initial limits are 2 GiB per source, 10 GiB total and a 1 GiB free-space reserve; all are adjustable. Limits include retained copies and staging space while a refresh is prepared. Unload a source before removing its in-use managed copy. This action never removes a linked user folder or checkout.
5. A standalone Blob source reuses its last complete copy while checking for updates at startup. A paired Blob/local folder compares at startup, Load and Refresh and requires review before any changes. Cancelling leaves it unloaded. Detected local changes also unload the pair immediately. An unchanged paired refresh retains resident file windows; an unload closes owned views and prevents pending reads from reopening them.
6. Live SQL uses the same Explorer behavior for SQL Server and Azure SQL Database. Qualification checks visibility/schema access for supported objects and SELECT access to table data. The query window accepts a single SELECT, including supported CTEs and typed parameters; its default result limits are 10,000 rows, 64 MiB and 30 seconds. Results are read-only, bounded and stored in temporary local files, with paging/filtering/sorting and export.
7. Snapshot capture/import retains the three existing acquisition routes. Unknown origins open the enrichment dialog, which provides a copyable metadata query. Matching imports offer append versus separate resource; Restore To remains separate. Refresh records an attempt independently of content versions, preserves unchanged revision timestamps and retains older captured table data. Missing requested tables are reported and skipped; the capture recipe remains saved.

**Upgrading existing local Surf2 data**

Opening a supported older relational database requests upgrade confirmation. The upgrade requires exclusive database access, creates and verifies a recovery package before conversion, and restores ordinary access after success or a handled failure. Close other Surf2 instances first. An abrupt process termination while SQL Server is in single-user mode may require restoring multi-user access as described by the startup error; the recovery package is retained. The schema-1/2 and package-1/2 input contracts remain frozen. Package 3 includes containers, alternate sources, origin and refresh records without secrets or managed cache paths. This compatibility upgrade is distinct from the deferred Azure persistence migration.

**Validation and limits**

The regression runner includes `--remote-folders`, `--source-ui`, `--live-sql`, `--resource-schema` and the existing scope, capture, storage and package suites. Git checks use real temporary repositories. Blob transfer/conflict/limit checks use a deterministic transport fixture. SQL checks use disposable local SQL Server fixtures, including denied-access accounts, unchanged/changed capture history, missing tables, origin matching, bounded queries and both reference-index paths. Scope UI checks render both themes and reduced layouts. Startup tests use owned recovery files and disposable databases.

Actual Entra/SAS authentication, private-network Azure connectivity and representative large remote datasets still require environment qualification with suitable test accounts. Cached content uses the local parsing/indexing paths; first fetch and refresh remain network-dependent, and no measured cross-network performance guarantee is claimed. Git trees requiring submodules, symlinks or Git LFS content are explicitly rejected in this implementation. Unsupported Windows filename collisions and ambiguous Blob directory-marker names are also reported before publication rather than silently losing content.

Surf2 persistence connection catalogues, database transfer/replacement, migration to shared Azure persistence, profiles and public/private sharing are not included in this delivery. Scheduled snapshot capture remains later work.
